# 0.1.0 — initial release

First public version of `@naskot/node-hmac-auth-management`. The lib packages the dynamic control-plane orchestration on top of `@naskot/node-hmac-auth >=1.4.0`.

## What it provides

- A single async factory: `createHmacAuthManagement(options)`.
- Two per-track surfaces (HTTP always, message optional) each exposing 9 methods: `add`, `update`, `remove`, `sync`, `get`, `list`, `health`, `healthAll`, `getDeliveryStatus`.
- A typed error class: `HmacAuthMgmtError` with the union `HmacAuthMgmtErrorCode`.
- A FROZEN derivation primitive: `deriveSecretV1(secretToken, propagationKey)`.

## Public surface

### Types

- `ManagedRow`, `ManagedRowCreateInput`, `ManagedRowUpdatePatch` — the single BDD row owned by the consumer.
- `DeliveryStateRecord`, `DeliveryStateUpdatePatch` — per-(row, target) cursor used by sync().
- `ManagedCrud` — the 10-method CRUD the consumer plugs in (4 reads, 3 mutations, 2 delivery-state callbacks, 1 propagation-key read).
- `CreateHmacAuthManagementOptions`, `ManagedTrackOptions`, `ManagementLogger`.
- `HmacAuthManagement`, `HmacAuthManagementTrack`.
- `TargetHealth`, `SyncSummary`, `ManagedRowWithSecretHash`.
- `AddTrackInput`, `UpdateTrackInput`, `RemoveTrackInput`, `GetDeliveryStatusInput`.
- Re-export of `InitializedHmacHttpAuth` and `InitializedHmacMessageAuth` from the upstream package.

### Behavior

- **Auto-seed** of the propagation-key row in the HTTP CRUD when missing at boot. Idempotent on repeated boots. The plain is `deriveSecretV1(secretToken, propagationKey)`. Restoring an older BDD dump that never held the row is recoverable transparently.
- **`sync()` orchestrates 4 phases per call**:
  - Phase A: probe every unique target seen in pending rows + the propagation-key row. Bootstrap the propagation key on targets that lack it (or were wiped). Detect Trap 4 (target reset: `clientsCount === 0` with a prior `delivered` cursor) and flip every row targeting that target back to `pending` for that target only.
  - Phase B: if the propagation-key row was `status: "pending"`, flip it to `ok` and clear the plain to `null` once it has been pushed.
  - Phase C: every `data_plane` row with `status: "pending"` is hashed with a fresh per-row UUID, propagated to every reachable target in parallel, atomically rolled back on partial failure (`DELETE` for create, `PATCH revert` for update). The BDD row flips to `ok` (secret cleared) on success or `error` (secret cleared, reason listed) on failure.
  - Phase D: every row with `status: "delete_pending"` (except the propagation key) sends `DELETE` to every target best-effort. Once every target reported, the row is purged from the BDD and the source-local credential is dropped.
- **`remove(propagationKey)` is refused** with `PROPAGATION_KEY_REMOVE_FORBIDDEN`. A `delete_pending` cursor on the propagation-key row is also skipped with a warn log: the lib never tears down its own signing credential.
- **Cross-token verifiability**: the lib NEVER re-hashes a credential on a target. The wire payload carries the locally-computed `secretHash`, the target stores it as-is. Source and targets can run with completely different `HMAC_SECRET_TOKEN` values; signed requests verify regardless.

## Atomicity rules per row kind

| Kind              | Status           | Atomicity                                                                                                                                                             |
| ----------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `propagation_key` | `pending`        | Non-atomic. Pushed to every target in parallel; a target that refuses does NOT trigger a rollback on others.                                                          |
| `data_plane`      | `pending`        | Atomic. Partial failure (or unreachable target) → rollback every accepted target via `DELETE` (effective create) or `PATCH revert` (effective update on v1.2.0+ TTL). |
| `data_plane`      | `delete_pending` | Non-atomic, best-effort. Target that refuses or is unreachable keeps the credential; the per-(row, target) cursor flips to `errored` so the next sync() retries.      |
| `propagation_key` | `delete_pending` | Skipped with a warn log.                                                                                                                                              |

## Compatibility

- Peer dependency `@naskot/node-hmac-auth ^1.4.0` is strict. v1.2.x and older are missing `purpose: "propagation-only"` and `requireBootstrapClientId`, both load-bearing for the lib's security guarantees.
- Storage-agnostic: the consumer plugs in any `ManagedCrud` implementation (TypeORM, Postgres native, Prisma, Mongo, REST proxy, in-memory Map for tests). The lib never assumes SQL.
- Framework-agnostic: the lib never imports Express, NestJS, or Nuxt. The POC demonstrates 3 framework integrations (NestJS, Express, Nuxt) by binding `sync()` to a `@Cron()`, a `setInterval`, and a Nitro background task respectively.

## Tests

- `auto-seed.test.ts` (5 cases): boot-time seeding, idempotence, 3 invalid-option paths.
- `sync.test.ts` (4 cases): end-to-end happy path with 2 cross-token targets, atomic rollback, remove flow, target reset detection.

Total: 18 vitest cases, all green.

## POC

- 4 services + 4 distinct Redis instances:
  - `api_a_nestjs`: the authority. Runs the management lib + drives `sync()`.
  - `api_b_nestjs`: a NestJS target.
  - `api_c_express`: an Express target.
  - `app_d_nuxt`: a Nuxt app whose backend integrates BOTH libs; the frontend lists every service's Redis contents side-by-side and exposes buttons to ping A / B / C via signed propagated credentials.

Each service initializes upstream `requireBootstrapClientId` so the first request the authority sends has to be the propagation-key bootstrap POST. Each service has a distinct `HMAC_SECRET_TOKEN` to prove cross-token verify works end-to-end.

## Out of scope (v0.1.0)

- A target whose Redis already holds other clients but NOT the propagation key cannot be bootstrapped (the upstream bootstrap window is only open at `clientsCount === 0`). Such targets must be set up manually before being managed by the lib.
- The optional message track reuses the HTTP propagation key for signing; a future v0.2.0 may revisit this if a message-only consumer requires a separate propagation key in the message CRUD.
- The lib does NOT start any scheduler. The consumer drives `sync()` from its own cron / route / queue / loop. `setInterval(() => mgmt.http.sync(), 5_000)` is a perfectly valid driver.
